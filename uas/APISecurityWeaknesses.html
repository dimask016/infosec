OWASP API Security – Part F

Question 11 – Short Answer

Identify three (3) API security weaknesses found in the PT GlobalRetail scenario.
Scenario Recap: Customer Rewards API – IDOR vulnerability (changing ID 1001 → 1002 returns other user’s data), rate limiting disabled, tokens valid for 90 days, public API docs, verbose DB errors, but HTTPS is enabled.

Tiga Kelemahan Utama

🔓 1. Broken Object Level Authorization (BOLA/IDOR) Kritis

Apa yang terjadi? Server tidak memverifikasi apakah pengguna yang terautentikasi memiliki izin untuk mengakses data pelanggan tertentu. Konsultan mengubah customer_id dari 1001 ke 1002 dan mendapatkan data pelanggan lain tanpa hambatan.

GET /v1/customers/1002 HTTP/1.1
Host: api.globalretail.com
Authorization: Bearer eyXXXXX // token milik user 1001, tapi data 1002 terbuka
Dampak
Eksfiltrasi data pribadi jutaan pelanggan (nama, alamat, poin, histori)
Akar Masalah
Tidak ada pengecekan otorisasi di sisi server; hanya mengandalkan ID dari input client
  • Rekomendasi: Gunakan ID pengguna dari token JWT yang sudah terverifikasi, lalu tambahkan klausa AND user_id = decoded_token.user_id pada setiap query. Ganti ID numerik dengan UUID untuk mempersulit enumerasi.
  • Referensi OWASP: API1:2023 – Broken Object Level Authorization (BOLA) – merupakan nomor satu dalam OWASP API Security Top 10.
Kunci: Jangan pernah mempercayai input dari client untuk menentukan kepemilikan data. Selalu binding dengan identitas pengguna yang terautentikasi.
🚫 2. Missing Rate Limiting Tinggi

Apa yang terjadi? Tidak ada batasan jumlah request per pengguna atau per IP dalam periode waktu tertentu. Attacker dapat mengirim ribuan request dengan ID yang berurutan (1001, 1002, 1003, ...) dalam hitungan menit tanpa terblokir.

Dampak
Memungkinkan brute-force enumerasi ID dan scraping data massal secara otomatis
Akar Masalah
Tidak ada mekanisme pembatasan request di tingkat API gateway atau aplikasi
  • Rekomendasi: Terapkan rate limiting dengan kebijakan misalnya 50 request/menit per user untuk endpoint sensitif. Jika terlampaui, kembalikan HTTP 429 Too Many Requests.
  • Praktik baik: Gunakan Redis atau layanan API gateway (seperti Kong, AWS API Gateway) untuk mengelola limit secara terpusat.
Manfaat: Selain mencegah scraping, rate limiting juga melindungi dari serangan DoS dan brute-force.
⏳ 3. Long-lived Authentication Tokens (90 days validity) Tinggi

Apa yang terjadi? Token autentikasi yang digunakan untuk mengakses API memiliki masa berlaku 90 hari. Jika token bocor atau dicuri, attacker memiliki jendela waktu yang sangat panjang untuk menyalahgunakannya.

Dampak
Token yang dicuri dapat digunakan berulang kali selama 90 hari untuk mengakses semua data yang diizinkan oleh token tersebut
Akar Masalah
Kebijakan masa berlaku token yang terlalu panjang tanpa mekanisme refresh atau revoke
  • Rekomendasi: Perpendek masa berlaku access token menjadi 15–30 menit. Gunakan refresh token (berlaku 7 hari) yang hanya digunakan untuk mendapatkan access token baru, bukan untuk mengakses data.
  • Tambahan: Terapkan token rotation dan revocation list untuk mencabut token yang mencurigakan.
Prinsip Keamanan: Semakin pendek masa berlaku token, semakin kecil risiko jika terjadi kebocoran.

Kelemahan Lain yang Ditemukan (tapi tidak termasuk 3 utama)

  • 📄 Publicly accessible API documentation – memberikan informasi endpoint dan skema request kepada attacker, memudahkan eksplorasi celah keamanan. Rekomendasi: pindahkan ke internal VPN atau proteksi dengan basic auth.
  • ⚠️ Verbose error messages (database details) – pesan error yang mengungkapkan nama tabel, kolom, atau struktur query dapat membantu attacker melakukan serangan lanjutan seperti SQL Injection. Rekomendasi: gunakan pesan error generik untuk client dan log detail di server.
  • 🔒 HTTPS encryption enabled – ini adalah kekuatan, bukan kelemahan. Sudah menjadi praktik yang baik dan harus dipertahankan.

Ringkasan Tiga Kelemahan

No Kelemahan Tingkat Risiko Solusi Singkat
1 BOLA/IDOR Kritis Binding otorisasi dengan token user, gunakan UUID
2 Missing Rate Limiting Tinggi Terapkan rate limit (misal 50 request/menit)
3 Long-lived Tokens (90 hari) Tinggi Access token 15–30 menit + refresh token

Ketiga kelemahan ini saling memperparah: BOLA memberikan akses data, rate limiting yang tidak ada memungkinkan enumerasi massal, dan token yang panjang memberi waktu bagi attacker untuk terus mengeksploitasi.
