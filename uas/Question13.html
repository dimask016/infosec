# API Risk ⟷ Recommended Control Detail
1 BOLA / IDOR Authorization Checks on Every Request

Mengapa kontrol ini adalah solusi yang tepat?

🔍 Bagaimana cara kerjanya?
Kontrol ini memastikan bahwa setiap permintaan ke API tidak hanya memeriksa keabsahan token (autentikasi), tetapi juga memverifikasi apakah pengguna yang terautentikasi memiliki izin untuk mengakses objek/data yang diminta. Di sisi server, ID pengguna dari token JWT di-binding dengan parameter query (misal: WHERE id = ? AND user_id = decoded_token.user_id).
🎯 Mengatasi akar masalah
Serangan BOLA/IDOR terjadi karena server tidak memeriksa otorisasi. Dengan menambahkan pengecekan otorisasi di setiap request, attacker tidak akan bisa mengakses data pelanggan lain meskipun mengganti ID di URL, karena server akan menolak akses jika ID tidak sesuai dengan pemilik token.
Referensi skenario: "The API returns another customer's personal information without verifying whether the user is authorized to access that record."
2 Excessive Requests API Rate Limiting

Mengapa kontrol ini adalah solusi yang tepat?

🔍 Bagaimana cara kerjanya?
Rate limiting membatasi jumlah request yang dapat dikirim oleh satu pengguna (atau satu IP) dalam periode waktu tertentu, misalnya 50 request per menit. Jika batas dilampaui, server akan mengembalikan status HTTP 429 Too Many Requests.
🎯 Mengatasi akar masalah
Tanpa rate limiting, attacker dapat melakukan enumerasi ID secara otomatis (brute-force) dalam skala besar. Dengan adanya batasan, upaya scraping massal menjadi tidak efektif karena attacker akan terblokir setelah mencapai batas request, sehingga mencegah eksfiltrasi data dalam jumlah besar.
Referensi skenario: "Rate limiting is not enabled" dan management khawatir "attackers could exploit the API to access large amounts of customer data."
3 Token Abuse (Theft / Misuse) Short-Lived Tokens and Token Rotation

Mengapa kontrol ini adalah solusi yang tepat?

🔍 Bagaimana cara kerjanya?
Mengganti token yang berlaku 90 hari dengan Access Token berumur pendek (15–30 menit) dan Refresh Token (berlaku 7 hari) yang hanya digunakan untuk mendapatkan access token baru. Token rotation memastikan bahwa setiap kali refresh, token baru dikeluarkan dan token lama tidak bisa digunakan lagi.
🎯 Mengatasi akar masalah
Token yang dicuri memiliki masa berlaku 90 hari, memberi attacker waktu sangat panjang untuk menyalahgunakannya. Dengan memperpendek masa berlaku, window of opportunity menjadi sangat kecil (15-30 menit). Jika token dicuri, kemungkinan besar sudah kadaluarsa sebelum sempat digunakan. Token rotation juga membatasi kerusakan jika terjadi kebocoran.
Referensi skenario: "Authentication tokens remain valid for 90 days."
4 Information Disclosure Generic Error Messages

Mengapa kontrol ini adalah solusi yang tepat?

🔍 Bagaimana cara kerjanya?
Mengganti pesan error yang detail (misal: SQL Error: column 'email' not found) dengan pesan generik (misal: {"error": "Terjadi kesalahan pada server"}). Semua detail teknis (stack trace, query SQL, nama tabel) hanya dicatat di log internal server.
🎯 Mengatasi akar masalah
Pesan error yang verbose dapat membocorkan struktur database (nama tabel, kolom) kepada attacker. Informasi ini bisa digunakan untuk menyusun serangan lanjutan seperti SQL Injection atau enumerasi skema. Dengan pesan generik, attacker tidak mendapatkan petunjuk teknis apapun, sehingga mempersulit eksploitasi lebih lanjut.
Referensi skenario: "Error messages reveal detailed database information."
