OWASP API Security – Part F

Question 14 – Analysis Question

A security consultant must prioritize one API vulnerability for immediate remediation. Which vulnerability should be fixed first and why?
Scenario Recap: IDOR (change ID 1001→1002 gets other's data) | No rate limiting | 90-day tokens | Public docs | Verbose DB errors | HTTPS enabled.
PRIORITAS #1 – REMEDIASI SEGERA 0-24 Jam
Broken Object Level Authorization (BOLA) / IDOR
Akses data pelanggan lain hanya dengan mengubah ID di URL — tanpa verifikasi otorisasi.

Dampak Langsung

Menimbulkan data breach instan. Attacker bisa langsung melihat data PII (profil, poin, histori) pelanggan lain tanpa hambatan teknis.

Mudah Dieksploitasi

ID numerik 1001, 1002, 1003 mudah ditebak. Tidak memerlukan alat canggih — cukup ubah angka di browser atau Postman.

Akar Masalah (Root Cause)

Merupakan business logic flaw di sisi server. Selama otorisasi tidak diperbaiki, kerentanan lain (rate limiting, token) hanya memperlambat, bukan mencegah, akses tidak sah.

Dampak Regulasi & Bisnis:

Kebocoran data jutaan pelanggan → Denda UU PDP / GDPR + Kehilangan kepercayaan pelanggan. Risiko ini tidak bisa ditoleransi dan membutuhkan perbaikan segera.

Analisis Perbandingan: Mengapa BOLA/IDOR Lebih Prioritas?

Kerentanan Apakah Ini Akar Masalah? Apakah Memungkinkan Akses Data Langsung? Kesimpulan Prioritas
BOLA / IDOR ✅ Ya — Server gagal memeriksa hak akses. ✅ Ya — Attacker langsung melihat data pelanggan lain. PRIORITAS #1 — Perbaiki sekarang!
Missing Rate Limiting ❌ Tidak — Hanya memperlambat serangan, tidak mencegah akses. ❌ Tidak — Tidak memberikan akses data secara langsung. Prioritas 2 — Penting untuk mencegah scraping massal,
tetapi tidak menghentikan IDOR itu sendiri.
Long-lived Tokens (90 hari) ❌ Tidak — Token yang valid digunakan oleh user yang sah untuk mengakses data orang lain. ❌ Tidak — Attacker menggunakan token yang sah untuk mengeksploitasi IDOR. Prioritas 3 — Memperpendek masa berlaku token penting, tetapi
tidak mencegah user melihat data orang lain.
Verbose Error Messages (DB details) ❌ Tidak — Hanya memberikan informasi tambahan (reconnaissance). ❌ Tidak Prioritas 4 — Risiko kebocoran informasi, tetapi
tidak menyebabkan data breach langsung.
Public API Documentation ❌ Tidak — Memberikan "peta jalan" kepada attacker. ❌ Tidak Prioritas 5 — Risiko informasi, tetapi
tidak memberikan akses data langsung.
Keputusan Akhir: BOLA/IDOR harus diperbaiki pertama kali karena:
  • ✅ Ini adalah root cause yang memungkinkan akses data tidak sah secara langsung.
  • ✅ Kerentanan lain (rate limiting, token, error) adalah faktor yang memperparah, tetapi tidak menyelesaikan celah akses data.
  • ✅ Selama otorisasi tidak diperbaiki, attacker tetap bisa mengakses data pelanggan meskipun rate limiting aktif (hanya lebih lambat) atau token diperpendek (tetap valid dalam jangka pendek).

Kesimpulan & Rekomendasi

Prioritas #1: Segera perbaiki validasi otorisasi di sisi server untuk endpoint /v1/customers/{id}. Binding setiap request dengan user_id dari token JWT yang terverifikasi. Jangan pernah mempercayai input ID dari client tanpa verifikasi kepemilikan.

Remediasi: Server-Side Authorization Check

Setelah BOLA diperbaiki, lakukan perbaikan bertahap: Rate Limiting → Token Expiry → Generic Error → Hapus Public Docs.
